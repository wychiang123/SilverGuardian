# MVP 分析

本文件根據目前 SilverGuardian 程式碼、`docs/requirements.md`、`docs/roadmap.md`、`docs/agent-guide.md` 推導最小可行產品（MVP）範圍。

> 若功能無法從目前程式碼完全確認，會標註「推測」。

## MVP 定義

SilverGuardian 的 MVP 應聚焦在一個最核心價值：

> 讓長者或需要協助的使用者，可以用最簡單的操作判斷收到的訊息是否可能為詐騙，並在高風險時取得家人協助。

因此，MVP 不應同時追求完整記帳、完整備忘、完整行事曆、照護者平台或後端管理系統。這些可以是後續擴充。

以目前專案定位來看，MVP 的最小閉環應該是：

1. 使用者拍攝或選擇疑似詐騙訊息圖片。
2. App 使用 AI 與基本規則判斷風險。
3. App 用清楚、長者友善的方式顯示結果。
4. 高風險時可以通知家人。
5. 使用者或家人知道下一步該怎麼做。

## 目前已完成的 MVP 功能

根據目前程式碼，以下功能已具備初步實作：

- 首頁入口。
- 拍照或從相簿選擇圖片。
- 呼叫 OpenAI 進行圖片分析。
- 本機詐騙規則引擎。
- AI 分數與規則分數合併。
- 風險結果頁。
- 高風險時嘗試透過 SendGrid 通知家人。
- 設定最多 3 組家人 Email。
- 本機每日使用次數限制。
- 語音記錄、Whisper 轉錄與 AI 分類。
- 本機歷史記錄。
- 行事曆寫入。

其中，與詐騙辨識 MVP 最直接相關的是：

- 圖片掃描。
- AI 分析。
- 規則引擎。
- 風險結果顯示。
- 家人通知設定。
- 高風險家人通知。

語音記錄、支出分類、備忘、行事曆與歷史記錄雖已存在，但對「詐騙防護 MVP」不是最小閉環必要條件。

## 必要

以下功能是 MVP 必要功能。沒有這些功能，產品核心價值不完整。

### 1. 圖片取得

使用者必須能提供疑似詐騙內容。

目前狀態：

- 已實作相機拍照。
- 已實作相簿選圖。
- Android 權限請求已有初步處理。

必要原因：

- 這是詐騙辨識流程的入口。
- 對長者而言，拍照或選截圖比複製文字更直覺。

### 2. 詐騙風險分析

App 必須能根據圖片內容產生風險判斷。

目前狀態：

- 已透過 OpenAI 分析圖片。
- 已有本機關鍵字與規則引擎。
- 已有 AI 分數與規則分數合併邏輯。

必要原因：

- 這是 SilverGuardian 的核心業務能力。
- 若沒有穩定風險判斷，App 只剩圖片上傳工具。

注意：

- 目前此邏輯集中在 `ScanScreen.tsx`，尚未獨立測試。
- MVP 上線前至少需要補詐騙規則與分數計算測試。

### 3. 清楚的結果顯示

使用者必須能理解目前是高風險、中風險、低風險或資訊不足。

目前狀態：

- 已有 `ResultScreen`。
- 顯示風險等級、分數、信心分數、證據、說明與結論。
- 低信心與人工複查提示已有初步呈現。

必要原因：

- 長者使用情境下，分析結果必須直接、清楚、可行動。
- 只顯示技術分數不足以形成產品價值。

建議 MVP 要求：

- 高風險時給明確警示。
- 資訊不足時提醒重新拍攝或請家人協助。
- 避免 debug 資訊在正式使用者介面中過度曝光。

### 4. 家人聯絡設定

使用者必須能設定至少一位家人或照護者。

目前狀態：

- 已實作最多 3 組 Email 設定。
- 已儲存在 AsyncStorage。
- 已有基本 Email 格式檢查。

必要原因：

- 長者面對高風險詐騙時，最有價值的下一步是找可信任的人確認。
- 家人通知是產品從「分析工具」變成「防護工具」的關鍵。

### 5. 高風險通知

當結果為高風險時，App 必須能通知家人。

目前狀態：

- 已透過 SendGrid 寄送 Email。
- 已在 `ResultScreen` 高風險時觸發。

必要原因：

- 這完成 MVP 的保護閉環。
- 若只顯示高風險但沒有協助機制，對部分長者仍可能不夠。

注意：

- 目前手機端直接持有 SendGrid key，正式化前有安全風險。
- MVP 若只做內部 demo 可接受；若要公開發布，建議改由後端寄送。

### 6. 基本錯誤處理

App 必須能處理常見失敗情境。

目前狀態：

- 部分 API 錯誤與權限拒絕已有 Alert。
- 仍缺少一致的錯誤處理與友善文案。

必要原因：

- 圖片分析與通知依賴網路和第三方 API。
- MVP 必須避免使用者遇到失敗時完全不知道該怎麼辦。

### 7. 基本測試安全網

MVP 至少需要能穩定執行測試。

目前狀態：

- TypeScript 檢查可通過。
- Jest 目前因 React Navigation ESM 與 native module mock 不足而無法穩定執行。

必要原因：

- 專案未來預計讓 Claude Code、Codex、OpenHands 等 AI Agent 維護。
- 沒有穩定測試，AI Agent 修改核心邏輯時風險很高。

## 重要

以下功能對產品完整度與使用體驗很重要，但不是詐騙防護 MVP 的最小必要條件。

### 1. 語音記錄

目前狀態：

- 已可錄音。
- 已呼叫 Whisper 轉文字。
- 已使用 OpenAI 分類為支出、備忘或行事曆。
- 已支援確認後儲存。

重要原因：

- 符合長者友善操作方向。
- 可增加日常使用頻率。

不是必要原因：

- 它不是詐騙辨識閉環的核心。
- 若 MVP 目標是防詐，語音記錄可先保留但不應阻礙詐騙辨識上線。

### 2. 歷史記錄

目前狀態：

- 已保存語音記錄。
- 已支援查看與刪除。

重要原因：

- 使用者可回看支出、備忘與行事曆紀錄。
- 未來也可擴充保存詐騙掃描結果。

不是必要原因：

- 目前詐騙掃描結果尚未保存。
- 對即時防詐 MVP 不是必需。

### 3. 行事曆寫入

目前狀態：

- 語音分類為行事曆時可嘗試寫入系統行事曆。

重要原因：

- 讓語音記錄更有實用性。
- 可提升長者日常輔助價值。

不是必要原因：

- 與詐騙辨識核心價值無直接關係。

### 4. 本機每日使用限制

目前狀態：

- 已使用 AsyncStorage 實作每日 99 次限制。

重要原因：

- 可降低 demo 或早期測試階段 API 濫用風險。
- 對成本控制有初步幫助。

限制：

- 本機限制容易被清除或繞過。
- 正式成本控管仍需要後端。

### 5. 隱私與敏感資訊處理

目前狀態：

- 尚未看到完整隱私同意流程。
- console log 可能輸出敏感資料。
- API key 仍在手機端使用。

重要原因：

- App 會處理圖片、語音、轉錄文字與家人 Email。
- 若要公開測試或上架，這會變成必要項目。

## 可延後

以下功能可以延後到 MVP 驗證後再做。

### 1. 完整後端平台

建議未來實作：

- OpenAI proxy。
- SendGrid notification proxy。
- 伺服器端 rate limit。
- 成本監控。
- 錯誤追蹤。

可延後原因：

- 若只是內部 prototype 或小範圍 demo，可先用目前手機端直連方式驗證流程。

注意：

- 若要正式上線，此項會從「可延後」升級為「必要」。

### 2. 完整照護者模式

推測未來功能：

- 家人端通知中心。
- 多照護者管理。
- 高風險事件列表。
- 遠端設定。

可延後原因：

- MVP 只需要能通知家人，不需要完整家人端系統。

### 3. 詐騙案例資料庫

推測未來功能：

- 常見詐騙手法資料庫。
- 規則包更新。
- 案例分類。
- 離線初步判斷。

可延後原因：

- 目前 OpenAI 加本機規則已可形成初步 MVP。
- 案例資料庫適合在收集真實使用回饋後再設計。

### 4. 掃描歷史保存

目前狀態：

- 尚未看到圖片掃描結果保存。

可延後原因：

- 即時判斷與通知比歷史保存更重要。

但建議：

- 若未來要追蹤高風險事件或提供家人回看，應列入下一階段。

### 5. 完整記帳系統

目前已有語音支出分類，但尚不是完整記帳產品。

可延後原因：

- 記帳不是防詐 MVP 的核心。
- 不應讓記帳功能擴張影響詐騙辨識品質。

### 6. 完整備忘與任務管理

目前語音可分類為 memo，但沒有完整任務管理。

可延後原因：

- 屬於日常輔助加值功能。
- 與高風險詐騙防護閉環無直接關係。

### 7. UI 大幅視覺重設

目前已有大字、大按鈕與基本顏色區分。

可延後原因：

- MVP 重點是流程可用與判斷可信。
- 視覺細節可以在核心流程穩定後迭代。

### 重要

- 語音記錄。

## 建議 MVP 驗收標準

MVP 可視為完成時，至少應符合：

1. 使用者能從首頁進入圖片掃描。
2. 使用者能拍照或選圖。
3. App 能回傳高、中、低或資訊不足結果。
4. 高風險結果有清楚警示。
5. 高風險時可通知至少一位家人。
6. 網路失敗、權限拒絕、AI 失敗時有可理解提示。
7. 測試可透過 `npm test` 穩定執行。
8. 詐騙規則與分數計算有基本測試覆蓋。

## 結論

SilverGuardian 的 MVP 不應定義為「長者生活助理全集」，而應定義為：

> 長者友善的圖片詐騙辨識與家人通知工具。

目前專案已完成許多 MVP 所需的功能雛形，但要讓 MVP 穩定可維護，最需要補強的是：

- Jest 測試環境。
- 詐騙規則引擎測試。
- OpenAI 回傳容錯。
- API key 與通知流程的安全性。
- 結果頁的正式使用者體驗。
